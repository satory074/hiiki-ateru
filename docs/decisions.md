# 決め方の記録

このゲームで「なぜそうしたか」の記録。いまの作りの説明は CLAUDE.md、ここは決めた経緯。

## 1. 最初の決定（2026-11-24〜25、grilling）

2026年11月に流行った「あなたの年齢を当てます」（KEPIGAME）と「ポケモンを11問で当てる」の流れで作った。
年齢当てと同じく「知っているものの偏り」から当てる。オーナーへの質問はダイアログで1つずつ聞いて決めた。

### 決定事項
| 項目 | 決定 |

### 当てる仕組み（`src/lib/model.ts`、`src/lib/select.ts`）
- **仮説は80個**：本命1球団（12）、2球団（66組）、贔屓なし（1）、野球を見ない（1）。
  - 掛け合わせる隠れた要素が2つある。詳しさ G（ライト／ふつう／コア）と、知ったかぶり O（低／高）。全部で 80×3×2 = 480 状態になる。
  - この規模なら近似せずに厳密にベイズ更新できる。
- **事前確率**：本命1球団 0.6（12球団で均等）、2球団 0.2（66組で均等）、贔屓なし 0.12、見ない 0.08。初期値として置き、答え合わせが集まったら手動で直す。
- **答え方の確率**：`P(答え | 関係, G, O, 知名度)` の表を使う。
  - 関係は、質問の対象球団がその人にとって何かで決める。ファン／同じリーグの他球団／別リーグ／贔屓なし／見ない。
  - 移籍した選手は、在籍したどれか1球団でもファン側なら「ファン」とみなす。
  - 知名度は B（野球好きなら名前は知っている）と C（その球団のファンでないとまず知らない）の2段階。誰でも知っているスター（A）は使わない。**→ 2026-11-25 に、名物だけ A（野球を見ない人でも聞いたことがある）を作った**
  - 表の初期値は `data/likelihood.json` に置き、手で決める。
- **確信度の膨らみすぎを抑える**：答えの確率を τ=0.7 乗で割り引く。この割り引きは完全な補正ではない。集めた答え合わせで「確信度80〜90%のとき、実際に何%当たったか」を比べて直す。
- **次の質問の選び方**：結果15種類に対するエントロピー（どれだけ迷っているか）が、一番減る見込みの質問を選ぶ（期待情報利得）。
  - 同じジャンルで「知らない」が3回続いたら、そのジャンルの点数を半分にする。
  - 架空の質問は、決めた番手（4・12・20・28問目）に入れる。**→ 2026-11-25 に窓（3〜5・8〜10・14〜18・22〜26問目）の中のくじに変更**
  - 地方の質問は、15問を過ぎても一番の確信度が50%未満で、利得も小さいときに1回だけ出す。
- **質問中は球団名を出さない**：選手には「投手・2010年代」程度の手がかりだけを付ける。どの球団の質問だったかは「答えた問題を見る」で明かす。
- **出力**：
  - 知識の偏り＝球団ごとの「ファン側である確率」。
  - 決め手＝最終結果と2位との差を一番広げた答え（対数尤度比が最大のもの）。
  - 知ったかぶり度＝架空の質問のうち、何問を「知ってる」と答えたか。

### 答え合わせの集計（Supabase、xword のプロジェクト）
**通すもの**
- 匿名の人が `public.hiiki_record_result(p jsonb)` を呼ぶことだけ（SECURITY DEFINER、`search_path=''`）。
- p の中身は、モデルの版、推定した結果、本当の答え（本命の球団 id か「なし」か「見ない」、ほかに好きな球団の配列）、答えの配列（質問 id と答え、30個まで）。
- 関数は数を足すだけ。足す先は `hiiki.result_counts(版, 日, 推定, 本命)` と `hiiki.answer_counts(版, 日, 質問id, 答え, 本命, ほか)`。

**拒否するもの**
- 表への直接の select／insert／update／delete（anon と authenticated のどちらも。`revoke all`）。
- 公開関数以外の関数の実行（`revoke execute`）。
- 実在しない球団 id や質問 id、31個以上の答え、大きすぎる p。いずれも例外で拒否する。
- **2026-11-25 に追加**: 登録の無い版（hiiki.versions）も拒否。1日の行数・表の大きさに上限（hiiki.limits）
- 一人ひとりの回答、IP、時刻は保存しない（記録は日単位まで）。

**読む人**：オーナーだけ。手元の `.env` に置いた service role キーを使い、`scripts/reflect.ts` で読む。キーは配信物にもリポジトリにも置かない。

**実行時の送信**：送れなかったら黙って捨てる。無料枠を超えても課金は発生しない。xword の keepalive がプロジェクトの停止を防いでいる。

**手動反映**：`scripts/reflect.ts` が次のことをする。
- 回答が50件以上ある質問について、実際の答え方の分布を出す（今の値を20件分として混ぜてならす）。
- 新旧の差分、シミュレーションでの的中率の変化、日ごとの急増などの異常を表示する。
- `--write` を付けたときだけ `data/likelihood.json` を書き換える。

## 2. 質問の仕方と炎上リスクのレビュー（2026-11-25）

テスト公開の当日に、オーナーの依頼で「質問の仕方」を厳しく見直し、炎上リスクをウェブでも調べた。

### 見つかったこと（重い順）
1. **現役選手の情報が古かった**: 今オフの戦力外・引退・FA 宣言・トレードで 12 人が球団違い・引退になっていた。
   照合が intai-fa の在籍記録（2025年まで）だけで、更新を「年1回3月」にしていたため。
2. **報道で名前が知られている選手**: ファンでなくても知っているので推定が崩れ、答えの一覧が選手を笑うネタにもなりうる。
   → オーナー判断で、報道だけを理由には外さない。どの選手の何の報道かは、このリポジトリに書かない。
3. **共有画像に「非公式」が無かった**: 画像だけが広まると公式と誤解されうる。
4. **答え合わせの集計が xword を止めうる**: 版を何でも受け付けたので、いたずらで行がいくらでも増え、同じ Supabase プロジェクトの無料枠を超えうる（超えると API が 402 で止まる）。
5. **前提を押しつける質問**: 「ひいきのチームが負けた日…」などに「贔屓がない」の答えが無かった（届いた答え合わせで実際に困っていた）。
6. **「知っている＝ファン」が地元・テレビの知識で崩れる**: 世間でも有名な名物、住んでいる土地のクイズ（何区・何市）、有名人と同じ名前の選手。
7. **架空の質問が弱い**: 番手が固定で見破れ、短く終わると1問しか入らず、名字の雰囲気で見破れ、実在のものと重なる名前があった。
   「知ったかぶり」という言葉は、詳しい人ほど知っている気がする（Atir ほか 2015）という研究に照らすと、熱心なファンを責める形になる。
8. 答えの段階に定義が無い、見ない人ほど問題が長い、確信度が当たる確率として確かめたものでない、何度でも送れる、からかいの決まり文句を止める仕組みが無い。

### 権利の見立て
- パブリシティ権: ピンク・レディー事件（最判 2012）の「専ら顧客吸引力を利用する」使い方に、無料・広告なしで名前を本文に書くだけのクイズは当たりにくい。応援歌は題名だけなら JASRAC の手続きは要らない。
- ただし球団の規程は法律より広い（選手氏名・マスコットの呼称を自分の財産として挙げる球団がある）。いちばんありそうなのは訴えではなく申し入れなので、申し入れがあればすぐ外すと about に書いた。

### オーナーが決めたこと
- 報道があった選手 → 外さない（古くなった選手だけ外すか OB に）
- 知ったかぶり度 → 「架空の名前チェック」に改め、2問以上出たときだけ、責めない文で出す
- 球団の規程 → 備えて続ける（共有画像にも非公式、連絡先は GitHub の issue、申し入れがあれば外す。広告・寄付は付けない）
- 範囲 → 見つかったことを全部直す

- 002 のマイグレーション（受け付ける版・上限）
